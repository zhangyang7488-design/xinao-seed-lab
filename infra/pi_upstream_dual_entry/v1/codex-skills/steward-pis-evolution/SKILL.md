## Preserve the stable relationship

- PiS is the primary working and evolution surface. PiB is the account-B, minimum-usable baseline
  and optional rollback/comparison surface. Two Codex accounts produce two isolated Pi auth/session
  profiles; that fact is not a two-product, two-role, or task-routing architecture.
- PiS is one working subject. Researching XINAO and improving its own body are activities chosen by
  the current object and parent result, not separate identities, sessions, or keyword routes.
- PiB receives only a proven, intersecting increment when a named B-side consumer exists. PiS
  maturity does not wait for symmetrical PiB optimization.
- The desired body is complete enough for real work but sparsely activated: mature organs remain
  cold until the task needs them, and no installed package gains agenda, authority, or completion
  identity.
- In this Skill, a Pi child means a Pi-native recursive thread/session spawned inside the addressed
  Pi harness, including a child spawning another child. It does not mean a Codex collaboration
  subagent or an external Grok/Terra/Luna WorkerPool. A model name such as Terra can appear in both
  worlds; identify the transport and session lineage before describing it.
- OpenAI-model Pi children follow the addressed profile's current account binding. A PiS binding
  change replaces only `prime-s`'s `openai-codex` credential and takes effect at a clean process
  boundary so the resumed root and every newly spawned child consume the same account. PiB follows
  the equivalent rule inside `prime-b`. Never copy OAuth, sessions, or child trees across profiles,
  and preserve independent native-provider credentials such as DeepSeek during an account switch.
- Treat the physical numpad bottom-right Enter as a PiS surface affordance, not a new submit
  convention: while the pointer is over the transcript it returns to the bottom and restores
  follow-output; while the pointer is over the input area it remains ordinary submit. Main Enter,
  Pi's native End behavior, mouse behavior, and PrimeB must remain unchanged. If exact terminal
  title, pointer geometry, or helper health cannot be established, fall back to ordinary Enter.
- Absorb Pi-owned terminal lifecycle cleanup. A temporary, failed, or stopped PiS TUI must not be
  left as a visible `process exited`/launch-error page for the user to sort out. Keep the dedicated
  `XINAO prime S` profile on `closeOnExit=always`, reap the exact helper and Pi process owned by the
  completed launch, and preserve the one live PiS consumer. Never kill the shared
  `WindowsTerminal.exe`, close a Codex tab, or turn cleanup of one known prior Pi surface into a
  desktop-wide enumeration project. If an already-detached legacy tab cannot be individually
  addressed, say so and leave that one manual residue rather than risk an unrelated live window.

## Use the real PiS maturity ruler

Ordinary TUI competence is only the floor: coherent conversation, direct file and shell work,
working tools, package registration, and a pleasant terminal surface do not establish mature PiS.
The intended advantage of the Pi harness must appear inside an authorized real activity. Look for
PiS to recover the live parent and evidence, form or revise its own local problem, recursively
organize genuinely independent labor when that has positive value, supervise and synthesize that
labor itself, retain useful failures and cross-turn learning, notice reproducible body friction,
and return to the same activity after an adopted body correction.

Codex must not manufacture a green demonstration by pre-slicing the scientific or other domain
problem into a small assigned task, remotely choosing every step, or treating tool/subagent counts
as the result. Give PiS the human parent, live object, real consumer, effect boundary, and Stop
conditions; let PiS form the local route and choose whether recursion is useful. Codex supervises
drift, boundaries, evidence, and real effect, and intervenes with steer or abort only when those
relations require it. Sparse activation still applies: mature PiS may correctly choose not to call
a child, search the web, write memory, or modify its body in a particular turn.

A successful real turn is evidence for one trajectory, not global maturity. Re-run the activity
across later turns and contexts, verify that retained learning changes behavior, and require body
evolution to pass the lab, adoption, fresh-consumer, rollback, and return-to-task loop below.

## Compile the Pi relationship, not a fixed ritual

When the user asks Codex to let Pi research, continue, supervise, or evolve, recover this complete
Pi-specific relationship without making the user restate it. Then select only the actions with
positive value for the current parent, live body, risk, and lifecycle stage. The Skill stores a
capability space, durable intent, correction history, and operating judgment; it does not require
every invocation to launch children, search, write memory, poll on a timer, change the body, run a
lab, or exercise every installed organ.

Construction and maturation periods legitimately use tighter observation, body labs, fault
reproduction, and repeated fresh-consumer checks. A mature steady period may use sparse dynamic
observation and long quiet intervals, intervening only when new evidence, drift, failure, risk, or
a high-value review point justifies it. Incident, recovery, and upgrade periods may temporarily
tighten supervision again. Do not freeze today's construction cadence into PiS's permanent working
personality.

Likewise, sleeping, scheduled wake, visible waiting state, periodic polling, and event-triggered
review are optional supervision mechanisms, not required Pi lifecycle states. Use one only when
the current Codex surface actually supports it, it reduces burden relative to a shallower route,
and sleeping itself does not spend model turns. Never simulate maturity with a long-running hook,
shell sleep, hidden second Codex, or a permanent monitoring controller. If no durable wake edge is
available, preserve the honest limit and use the shallowest bounded observation that serves the
current task.

## Keep PiS observable without turning it into noise

The user wants the visible PiS thinking stream when it is written in natural Simplified Chinese.
Do not solve English `Planning`/`Designing`/`Evaluating` fragments by hiding all thinking or leaving
only a spinner. Keep PiS thinking blocks expanded by default, preserve `Working...`, tool cards,
subagent foreground/background and lane state, failures, and recovery signals, and keep `Ctrl+T` as
the user's temporary fold. This concerns user-visible reasoning summaries; it does not lower the
model's thinking level or require disclosure of unavailable hidden model state.

At a material evidence change, route change, body friction, recovery, or return point, PiS should
emit a short natural Chinese progress paragraph that says what became known, why the route changed,
and what it will do next. Ordinary mechanical steps should remain compact. Codex supervision must
read these semantic updates together with addressed runtime events and real artifacts: neither a
motionless summary-only screen nor an endlessly spinning activity marker is sufficient evidence
that PiS is healthy.

Persist stable Pi-specific user corrections and reusable Codex-to-Pi operating judgment in this
source Skill or the durable family contract. Put drift-prone observed versions, body state,
credentials status, live capabilities, and limitations in the capability lineage. Leave transient
turn details in the native session or run evidence. This separation lets later windows recover the
relationship without turning every incident into a permanent command.

## Evolve from real work

1. Start from an authorized real activity and retain its exact return point.
2. Observe a reproducible friction. Separate a task-local mistake, upstream defect, missing
   knowledge, and Pi-body gap before proposing construction.
3. Research the mature external capability and collide it with the live PiS body. Existing organs,
   replacements, conflicts, noise, and unknowns stay separate.
4. Build the smallest coherent candidate in an isolated PiS body lab. Do not mutate PiB, copy
   sessions, rebind accounts, or expose secrets in source, commands, logs, or receipts.
5. Exercise positive, negative, failure, restart, rollback, and real-consumer paths. A package load
   or self-report is not adoption.
6. Codex compares the effect and adopts, narrows, rejects, or keeps the candidate experimental.
   Adopt only the intersecting PiS layer, then fresh-launch the desktop consumer.
7. Return PiS to the same real activity and determine whether the friction actually decreased.
8. Update the Pi capability lineage and surface evidence with observed facts, known-good rollback,
   and remaining limits. Do not turn one incident into a universal rule.

The user should see the current purpose, route-changing findings, actual consumer effect, and honest
limits. They should not have to repeat known paths, credentials, account relationships, or already
verified communication semantics.
