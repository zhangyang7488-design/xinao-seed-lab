# Steward the current Pi

Use this Skill when Pi itself is the active object: launching, observing, steering, repairing,
upgrading, testing, snapshotting, or recovering the user's Pi. It is a Codex-side operating
capability, not a second Pi architecture or a standing supervision loop.

## Start from the live activity

Bind current human words, the still-live parent, the exact Pi consumer, allowed effects, and Stop
before choosing a tool. Quoted designs, old Pi contracts, transcripts, reports, file names, and
installed packages are evidence; they do not appoint a role or restore a task.

Read only the intersecting sources:

1. `E:\XINAO_RESEARCH_WORKSPACES\pi-local-cognition-contract-island\AGENTS.md` for local
   identity, account, backup, compatibility, and recovery boundaries.
2. `E:\XINAO_RESEARCH_WORKSPACES\pi-local-cognition-contract-island\cognition\CURRENT_CAPABILITY_LINEAGE.md`
   for dated observations; verify versions, packages, credentials, processes, sessions, tools, and
   API behavior live.
3. `E:\XINAO_RESEARCH_WORKSPACES\prime-s-local-cognition-island\AGENTS.md`, the addressed
   launcher/profile, and the current official Pi installation for the active body.
4. A target repository's local instructions and real consumer only when the current Pi activity
   actually enters that repository.

Current words and live facts override every stored source. Missing continuity fails open to the
current object; it never invents work.

## Preserve only stable machine boundaries

- `prime` is the user's unqualified main Pi. `prime-s` is its current internal compatibility
  profile name, not a second product or S identity.
- Account binding selects authentication and quota for that profile. It does not select a task,
  epistemology, role, or product identity.
- `C:\Users\xx363\PrimeB.lnk` is an isolated cold backup. Keep its OAuth, profile, native
  sessions, running child state, surface state, and entrypoint separate. Open it only when the user
  names it or main-prime recovery genuinely requires it.
- Owner belongs to a named live effect scope. Pi, Codex, a model, a repository, a child, or a full
  prompt does not own effects by essence.

Everything else is versioned capability. Upstream Pi may add, replace, or remove models, tools,
extensions, child mechanisms, recursion, session behavior, waiting, recovery, and UI surfaces.
Describe what the current consumer proves; do not turn today's implementation into tomorrow's
contract.

## Discover the current official body

Before changing Pi, inspect the exact installed version, profile, launcher, process, native session,
provider/account binding, extension/package set, and the current official command/API surface
intersecting the task. Prefer upstream behavior over local emulation when it now covers the need.

Classify a local overlay as one of:

- still required for a verified local consumer;
- temporarily compatible with the current upstream version;
- superseded by upstream and ready for bounded retirement;
- stale or unverified and therefore not safe to present as capability.

A path, package registration, schema, or self-report proves presence only. Prove capability through
a fresh addressed consumer and preserve the version boundary of that evidence.

## Operate through real Pi edges

For an interactive Pi process, use the Codex/S-side mechanical client and protocol note:

- `E:\XINAO_RESEARCH_WORKSPACES\S\infra\pi_upstream_dual_entry\v1\operator-tools\pi-native-ingress\pi-native-control.mjs`

These operator files stay outside Pi's active Skill directory. The profile-local ingress is only
the addressed transport endpoint; installing its operating instructions into Pi would incorrectly
turn an external control edge into Pi's self-description.

Resolve the exact profile, process, session, cwd, busy state, and event sequence before mutation.
Use native prompt, steer, follow-up, abort, and stop according to their current semantics.

Keep the evidence ladder:

`sent -> acknowledged -> runtime accepted -> message consumed -> turn settled -> artifact -> consumer effect`

An acknowledgement is not understanding or completion. Read the native transcript, produced
artifact, and real consumer. Do not edit session JSONL, attach a second writer, or simulate input
when a supported edge exists.

Root/child behavior is whatever the addressed live Pi version actually implements. A child or
external worker returns candidate evidence unless current effect scope says otherwise. Do not make
"root supervisor", "child executor", recursive hierarchy, fixed model assignment, or mandatory
fanout part of Pi's identity.

## Upgrade or evolve without freezing Pi

Use real friction or an explicit upgrade request:

1. Capture the current version, consumer, failure/effect, rollback point, and unrelated dirty state.
2. Check whether current upstream Pi already supplies a mature replacement.
3. Make the smallest coherent change in the correct profile or overlay; keep PrimeB and unrelated
   sessions isolated.
4. Exercise intersecting positive, negative, failure, restart, and rollback paths.
5. Fresh-launch the actual desktop/native consumer and read back the effect.
6. Let the currently appointed effect Owner adopt, narrow, reject, or retire the candidate.
7. Record only dated capability evidence and recovery information that will reduce future burden.

A successful test covers that version and surface. It does not prove permanent Pi maturity or
justify a resident self-auditor, scheduler, role ontology, or control plane. When upstream covers a
local seam, prefer retiring the seam and its tests over preserving compatibility ceremony.

## Address external transport and observation mechanically

Use an external transport/observation edge only when the current activity addresses its exact Pi
profile, instance, session, and named mechanical scope. Within that scope it may transport a
message, observation opportunity, or stop request; the live activity supplies the meaning.

## Visible behavior and user burden

Keep the user informed in short natural Chinese about the current purpose, material route changes,
real effects, failures, and recovery. Preserve the visible interactive Pi window while keeping
non-interactive helpers hidden. Do not leave failed or completed helper windows for the user to
sort out.

Do not ask the user to repeat known paths, account relationships, or already verified communication
details. Ask only for a real user-only fact, value choice, missing secret, new external audience,
payment, irreversible action, or major external effect. Explicit Pause/Stop halts the addressed
effect path and prevents queued continuation.
